# Orbit orchestration in Antigravity desktop

Apply the `orbit` lead agent in `.agents/agents/orbit.md` and the specialist definitions under `.agents/agents/`. **The active Antigravity model is the reasoning engine.** Do not start Gemini CLI, Claude Code, or Codex CLI for Orbit.

- On start/resume, check project identity, Git state, compact `.orbit/PROJECT.md` and checkpoint `.orbit/STATE.md` **if present**; call `orbit_project_resume` when connected. Inventory canonical doc paths without bulk-reading their contents. Open only the sections and files needed for the current task; extend analysis when scope, risk, or decisions materially change.
- **Enforced intake gate:** call `orbit_intake_status`, `orbit_intake_propose`, record each answer with `orbit_intake_answer` and ask dependent questions via `orbit_intake_followup` only when the previous choice warrants it, then after genuine user answer or delegated defaults `orbit_intake_approve`, before first `orbit_build_begin`; new builds HOLD otherwise. Existing builds resume without re-interview. Periodically re-run `orbit_docs_audit` with growth signals and revise missing/outdated docs without duplication. `orbit_autonomy_review` recommends gradually reducing routine questions from guided to assisted/trusted, with explicit consent and no high-risk permission bypass.
- **Fresh project preflight (before a stack or PLAN):** load `references/PROJECT-INTAKE.md`. Interpret everyday requests such as 'build a todo app', classify product type, complexity, maturity and risk; ask the most important question **first** with a **Recommended** choice, then adapt the next question to the actual previous answer (typically 2–5 total, max 6). Offer **Use recommendations** to accept unambiguous defaults. Await answers unless user explicitly chose defaults. Do not reinterview a resumed/established project.
- **Documentation before implementation:** load `references/DOCS-AND-CONTEXT.md`, inventory owner docs by purpose, create only necessary nonduplicate vision/architecture/roadmap/design and product-type-specific docs through writer/architect or the lead host when delegation is unavailable. `.orbit/PROJECT.md` is an approved compact index to canonical owner docs, not a rival source. Produce a compact faithful agreed brief and targeted references, not recurring enormous prompts.
- **Reuse prebuilt capabilities before custom code:** audit native libraries and approved installed skills/MCPs and compare viable maintained external libraries for data/date rules, validation, UI and browser QA. Reuse existing trusted components when appropriate; document a concise choice and request consent before new installs. Vercel Labs agent-browser is for browser QA, not a UI kit.
- Plan milestone → gate → executable steps, including frontend, backend, data, security, tests, CI/CD and deployment when applicable. Detail the nearest milestone and avoid overengineering.
- Delegate with host-native `invoke_subagent` only if genuinely available and authorized. Before dispatch, preview/register a stable scoped task (`orbit_task_plan`) and reserve a slot (`orbit_task_reserve`) using the real user/host approval; after successful native invocation record its real session reference (`orbit_task_started`). Release failed reservations. This MCP never launches an agent or runs a model. The orchestrator owns task selection, dependencies, file boundaries, review, and next steps; child agents never self-authorize more spawning.
- Prefer isolated branches/worktrees for simultaneous code changes if the host supports them. Otherwise do tasks serially. Never edit overlapping files concurrently.
- Agents return verifiable diffs, tests, status and blockers; Orbit checks the actual diff and tests, then records task outcome (`orbit_task_report`) and separately reviewed acceptance (`orbit_task_review`) before dependent tasks. Neither reported evidence nor task review is independently attested by MCP.
- Save checkpoint to `.orbit/STATE.md` through `orbit_project_checkpoint` with fresh revision and explicit approved `confirm_write`. Preserve existing user documents/ADRs and do not duplicate source of truth.
- Memory is SQLite local only when MCP connected. No remote API, paid model, automatic agent process, cloud sync, or user data export is implied by skill installation.

Read `references/TASK-LIFECYCLE.md` for the native agent ledger workflow and `references/HANDOFF.md` for a bounded handoff. Apply only when delegation is actually needed.

## Local application preview (v0.24 feature candidate)

For a new app, after approved implementation, inspect the actual package scripts, plan tests, and prefer the existing IDE browser. To preview the running app, call `orbit_preview_start` with `confirm_run: false` to show the **exact** shell-free argv and loopback URL. Re-run with `confirm_run: true` only after actual user/host permission to execute that project's code; use `orbit_preview_status` and inspect readiness and logs. Open the returned `http://127.0.0.1:<port>/` using an available host browser. Run real user interaction tests through the host browser or Playwright only when installed and permitted. If the host separately exposes approved Vercel Labs `agent-browser` MCP tools, use accessibility snapshots and authorized DOM interactions as supplemental evidence, not as an automatic replacement for Orbit's gated Playwright verification. Configure localhost domain allowlists; no auto-install, browser credential/profile reuse, remote navigation or public sharing. See `docs/AGENT-BROWSER-OPTIONAL.md` in the Orbit repository. Do not equate HTTP 200 with UI test success. Use `orbit_preview_stop` with `confirm_stop: true` to shut down the locally managed process when finished.

No cloud deployment, public tunnel, remote sharing, third-party auto-install, or background AI agent execution is included in these MCP tools. The preview's process tracking lives only in the active MCP process; after a host/MCP restart it cannot safely adopt or stop previously spawned processes.


## End-to-end local app workflow (v0.24 candidate)

When user asks to build an app from one prompt, first audit existing work and complete the approval-gated intake (or user-delegated defaults), then begin the build in RESEARCH. Research proportionately, prepare concise documents and an editable user-approved plan **before** IMPLEMENT. Use the host's normal coding and agent abilities. Sequence: (1) audit → accepted brief → `orbit_build_begin` → RESEARCH, (2) right-sized approved plan/milestone/API contracts, (3) skill selection plus approved native specialist task delegation or serial implementation, (4) independent CLI tests and diffs, (5) permissioned `orbit_preview_start` and READY probe, (6) permissioned `orbit_browser_qa` with at least one actual user interaction and screenshot, (7) reviewer verification / repairs with bounded retry budget, (8) `.orbit/STATE.md` via guarded checkpoint, and (9) advance to DONE. Call `orbit_build_status` on resume to avoid repeating completed stages; its SQLite ledger tracks evidence, not invisible background model work.

`orbit_build_advance` records bounded caller-reported evidence; PREVIEW stage requires a currently READY Orbit-owned preview and preview_id, BROWSER_QA requires a recorded passing interactive Playwright result, CHECKPOINT requires an Orbit-managed checkpoint. Treat failed browser/CLI tests as blockers and use the host's approved repair ability; do not bypass a blocked gate. Browser QA is optional if unavailable, but then the run remains on HOLD rather than claiming success. Never expose public tunnels/deploy/commit/merge without distinct user permission. The local preview process still needs cleanup before closing MCP; across host restarts the *build state* is durable, not the running preview process.


## Research, verify and specialized skill preflight (isolated branch)

**New build IDs** use RESEARCH → PLAN → IMPLEMENT → VERIFY → PREVIEW → BROWSER_QA → REVIEW → CHECKPOINT → DONE; existing SQLite build records preserve their current stage and revision. RESEARCH requires a bounded JSON string containing `task`, `candidates`, `decision`, `sources` and `risks`. VERIFY requires JSON `commands` with reported zero exit codes, `edge_cases` and `security`. The host actually researches and executes tests; the MCP checks recorded fields, not independent truth. Use `orbit_capability_select` with the assigned agent name at the start of objective to get preferred specialist skills. Verify skill installation, provenance, suitability and actual execution; otherwise use native host fallback without any install. Read `references/COMPONENT-REUSE.md`.


## Scram/Emergent/Lovable-inspired UX without unnecessary IDE work

Offer two explicit workflows at the first unspecific request: **Scope first (recommended for unknown/high-impact requirements)** or **Build with sensible defaults**. A user who delegates defaults still gets a short visible proposed scope. Ask only the highest-impact question, conditionally adapt later questions to answers, and use a compact editable **plan preview** with title, outcome and 3–8 real tasks. On fresh builds, PLAN PASS now requires `approval_method` and `approval_reference` in JSON evidence; the host must show the plan and obtain actual approval (or explicit delegated build authorization). The MCP cannot authenticate user consent. Never silently claim a plan was approved. The existing task ledger handles subtask ownership/status; present concise progress, blockers, file changes and next action when the host UI supports it.

**Do not read every Orbit reference file or the whole project on every turn.** Load this skill and `.orbit/PROJECT.md` / `.orbit/STATE.md` if available, then only the relevant current-role reference and target file snippets. Read PROJECT-INTAKE for a new project, COMPONENT-REUSE for a research/reuse task, HANDOFF for delegation, DOCS-AND-CONTEXT for documentation updates, and TASK-LIFECYCLE for complex orchestration. On simple edits, inspect the affected files and run targeted tests; use a short decision note rather than a large research report. Call expensive web research only for genuinely changing niche dependencies, unverified choices or substantive risk. Reuse agreed decisions instead of repeatedly re-reading all history. No model can guarantee reduced billing; keep essential security/acceptance facts.
